2. Problems with the Existing System

Under conventional institutional email systems and unhardened mail servers, electronic communications suffer from four foundational security vulnerabilities:

  • Opportunistic Cleartext Fallbacks & STARTTLS Stripping (RFC 3207): Traditional Mail Transfer Agents (MTAs) negotiate encryption opportunistically via the STARTTLS command on Port 25. If an active network attacker performs a STARTTLS-stripping attack, the communication channel silently falls back to unencrypted cleartext ASCII transmission, exposing login credentials and confidential student records.
  • Email Spoofing, Header Discrepancy & Sender Impersonation: Legacy SMTP inherently decouples the transport envelope sender (MAIL FROM:) from the presentation header (From:). Because traditional MTAs accept incoming connections without cryptographically validating domain ownership, external malicious actors can inject forged emails claiming to originate from college administrators (e.g., director@jims.edu, placement@jims.edu).
  • Surveillance via Hidden Tracking Beacons (Web Bugs / Spy Pixels): Inbound marketing and spear-phishing emails frequently embed invisible 1×1 or 0×0 transparent GIF/PNG image tags. When a recipient opens the message, the client automatically executes an outbound HTTP GET request, covertly leaking the user's public IP address, physical location, and reading behavior.
  • Mutable, Non-Verifiable Server Logs: Standard mail servers write events to flat ASCII text files (/var/log/mail.log). These files lack cryptographic hashing or forward secrecy; rogue users or compromised root accounts can erase, truncate, or tamper with logs without detection.
  • Prohibitive Recurring Licensing Costs: Commercial cloud services charge $6.00 to $12.00 per mailbox monthly. For an institution with 2,000 accounts, this creates an annual financial drain of ₹1.2 Crore to ₹2.4 Crore.

3. Description of the Proposed System

The proposed system, SecureMail, is an integrated, self-hosted, cloud-capable web email platform engineered to eliminate the architectural flaws of traditional email transport. Engineered specifically for institutional and academic networks, SecureMail establishes a sovereign, zero-trust communication infrastructure.

Core Architectural Features:

  • Mandatory Wire-Level Encryption: Enforces strict TLS 1.3 across submission (Port 587) and inbound relay (Port 25) sockets using high-security cipher suites (TLS_AES_256_GCM_SHA384 and TLS_CHACHA20_POLY1305_SHA256) with zero unencrypted fallback.
  • Cryptographic Anti-Spoofing Gateway: Performs real-time DNS SPF record verification, validates 2048-bit OpenDKIM cryptographic signatures, and enforces strict DMARC alignment (p=reject) to immediately reject impersonation attempts with SMTP 550 codes.
  • In-Memory Privacy & Tracking Pixel Stripper: Fast in-memory HTML body parser intercepts incoming MIME streams in RAM and purges hidden tracking beacons before disk spooling or mailbox delivery.
  • Tamper-Evident SHA-256 Merkle Audit Ledger: Cryptographically chains each operational event to preceding block hashes, producing an append-only ledger that detects any retroactive log tampering.
  • Modern Dual-Client Application Suite: Provides a responsive Django 5.x Webmail portal and Flutter 3.x native mobile client with visual trust indicators (Green Lock for TLS 1.3, Blue Shield for DKIM authentication).

4. Description and Identification of Functional Modules

The system is organized into five tightly coupled functional modules:

  1. Mail Ingestion & Transport Security Engine: Manages SMTP socket negotiations, enforcing mandatory TLS 1.3 with AES-256-GCM cipher armor and terminating unencrypted connections at the socket layer.
  2. Anti-Spoofing & Identity Verification Gateway: Validates incoming DNS SPF TXT records, verifies 2048-bit OpenDKIM cryptographic signatures, and strictly enforces DMARC p=reject alignment.
  3. In-Memory Privacy Sanitizer: High-performance regular expression stream parser that detects and neutralizes zero-dimension (0x0, 1x1) tracking beacons in RAM within microseconds.
  4. Cryptographic Audit Ledger Module: Computes deterministic SHA-256 block hashes linking sequential security events into an immutable, chained audit ledger for forensic non-repudiation.
  5. Webmail Client & Mailbox Management Portal: Delivers an intuitive three-pane webmail interface and cross-platform mobile client with real-time security badges.

Identification of Users & Stakeholders

  • Campus Students: Access secure webmail and mobile client, compose and receive encrypted messages, view security badges, and exchange academic assignments safely.
  • Faculty Members & Mentors: Broadcast verified departmental communications and coordinate academic reviews without spoofing risk.
  • Administrative Officers: Dispatch sensitive institutional notices, fee receipts, and placement offer letters.
  • System Administrators: Monitor daemon health, manage mailbox quotas, and mathematically verify audit ledger integrity.

Security Defense-in-Depth Pipeline Flow

Every transaction proceeds through five sequential security gates:

[Inbound Socket] ➔ Gate 1: Mandatory TLS 1.3 Handshake (AES-256-GCM)
                 ➔ Gate 2: SPF + 2048-bit OpenDKIM + DMARC p=reject
                 ➔ Gate 3: In-Memory Regex Tracking Pixel Purging
                 ➔ Gate 4: Dovecot Maildir Local Mailbox Storage
                 ➔ Gate 5: SHA-256 Merkle Chained Audit Ledger Logging

6. Methodology

6.1 SDLC Model to be Used

The project adopts an Iterative Waterfall / Agile Hybrid Model. This methodology divides the project life cycle into disciplined, sequential phases (System Analysis, Protocol Hardening, Subsystem Implementation, Security Verification, and Final Documentation) while enabling iterative micro-cycles for testing individual cryptographic filters and user interface components.

6.2 Justification for the Selection of Model

Developing an enterprise email system requires rigorous network-level protocol compliance (RFC 8446 for TLS 1.3, RFC 6376 for DKIM, and RFC 7489 for DMARC). The iterative hybrid approach allows transport sockets and Milter filters to be rigorously tested for socket stability and RFC adherence before proceeding to higher-level web interface construction, ensuring zero architectural regressions.

6.3 Implementation Timeline & Roadmap

The implementation schedule spans the 12-week MCA Semester-III calendar: Weeks 1–2 (Requirements & Threat Modeling), Weeks 3–4 (MTA Socket Hardening & TLS 1.3 Binding), Weeks 5–6 (DNS SPF/DKIM/DMARC Gateway), Weeks 7–8 (In-Memory Privacy Filter & Merkle Ledger), Weeks 9–10 (Webmail Portal & Flutter App Integration), Weeks 11–12 (Test Matrix Execution & Final Review).
